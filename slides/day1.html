Course philosophy

Build it by hand first, then use the frameworks

  • First principles. You write the loop, the tools and the harness yourself, so every framework afterwards is "a harness someone else wrote".
  • Vendor-neutral, vendor-literate. The OpenAI and Anthropic APIs set the shapes that the rest of the industry copies, so we learn them in depth and run them on open models.
  • Measure, don't vibe. From Day 3, every change is checked against an eval suite.
  • Free models only. Every lab runs on free API models through OpenRouter. Nothing runs a model on your laptop.

We assume

Comfortable Python; you have called an LLM API before (Applied NLP or equivalent).

You don't need

A GPU, paid API credits, or experience with agent frameworks, MCP or LangGraph.

You leave with

An evaluated, secured agent service, your own harness, and the judgment to choose between build, SDK and hosted.

Collect answers by show of hands. Don't resolve it yet; the next slides give the definitions. Answer: C is an agent. B is a workflow (code decides the path). D is a loop around an agent. F is a graph with an agent inside a node. A is a prompt. E is marketing. The ladder again: prompt (A), agent (C), loop (D), graph (F).
Definitions

An agent is a model using tools in a loop

An LLM agent runs tools in a loop to achieve a goal.
Workflows: LLMs and tools orchestrated through predefined code paths. Agents: LLMs dynamically direct their own processes and tool usage.

Who decides the next step?

Your code → workflow. The model → agent. Real systems mix both.

Who decides it is done?

The model (no more tool calls), with the harness as a backstop (budgets).

Start simple

One call if it works; a workflow if the path is known; an agent only when it isn't.

Why items

Reasoning, tool calls, tool results and messages are separate, typed things that a loop handles one by one.

instructions

The system prompt is a parameter, not a message. Resend it on every call.

An SDK helper joining the text of message items. Agents read output.

Tool results go back as {"role": "tool", "tool_call_id", "content"} messages in Chat Completions and as {"type": "function_call_output", "call_id", "output"} items in Responses. Note that the Responses tool definition is flat: no nested "function" object.

Ask for a schema; validate anyway

class Triage(BaseModel):

Strict = constrained decoding

Where supported, decoding is constrained to the schema (OpenRouter: structured_outputs).

Not every model enforces it

Some free models treat the schema as a hint. Validation is your safety net either way.

The rule

Request strict where supported → validate always → repair once → fail loudly.

Chat Completions: response_format={"type": "json_schema", "json_schema": {...}}. Messages: output_config.format (Session 3).

Who keeps the conversation?

Stateless replay vs. server-side state

Stateless: resend everything (store=False)

history += r.output                # items as returned
history.append({"role": "user", "content": next_q})
r = client.responses.create(model=MODEL, input=history,
                            instructions=SYSTEM, store=False)

Works on every server (OpenRouter, vLLM, Ollama). You own the history, so you can trim, compact and audit it. This is what the labs use.

Stateful: OpenAI keeps it

  • previous_response_id=r.id: chain from the last response.
  • Conversations: a durable conversation object you pass as conversation=.
  • background=True: long tasks run server-side; poll or stream later.
  • Compaction (/responses/compact): the server shrinks a long history into an opaque item.

Less to send, more lock-in. Reasoning items can be passed back encrypted when store=False.

The stretch in Lab 1.2 sends previous_response_id to OpenRouter and gets an error: that's the point. Most engines implement the stateless subset of Responses. Day 2 returns to compaction and context editing in both APIs.
Tools the API runs for you

Function tools vs. hosted tools

Tool typeWho runs it
functionyou: the model asks, your code executes
web_search, file_searchthe API provider
code_interpreter, shell, computer usethe provider, in a container

Convenient

No loop code for those tools: one request can search, run code and answer.

But

They're vendor-specific, they run outside your permissions and logs, and open-model servers rarely implement them. In this course, tools are functions you run; MCP comes on Day 2.

Portability

Open Responses: one agent API shape across vendors

  • January 2026: OpenAI published the Responses shape as an open specification, Open Responses.
  • Implemented by OpenRouter, Hugging Face, vLLM, Ollama, LM Studio, NVIDIA and AWS, usually the stateless core: items, function tools, structured output, streaming events.
  • Vendor extensions (stored state, hosted tools) stay vendor-specific.
Practical rule. Write agents against the portable core (items, function tools, text.format, store=False), and treat everything else as an optional, swappable extra. That's how agentkit.ResponsesShape works.

One tool round trip

tool_use out, tool_result back, matched by ID

user"Status of REN-10482? ID ends 4821, mobile 0501234821."
assistant[text] "Let me check." [tool_use] id: toolu_01 get_permit({"permit_id": "REN-10482", …}) · stop_reason: tool_use

assistant[text] "Your renovation permit is under review. The decision is due by 2 November 2026." · end_turn

Append the assistant turn as is

All its blocks, including text and thinking, unchanged.

Results are a user turn

Every tool_result of one turn goes in one user message. Splitting them teaches the model to stop calling tools in parallel.

Errors are results too

"is_error": true with a message the model can act on.

  • Name what it does, one job per tool; namespace related tools (permits_get, permits_search).
  • Fewer, higher-level tools beat many thin API wrappers. Every definition costs context on every call.
  • Enums for closed sets, units in descriptions, sensible defaults.
  • Return what the model needs next: concise, with IDs it can reuse; paginate large results.
  • Errors as instructions: "SGN fee needs sign_m2", not a stack trace.

def my_agent(task, tools, system, max_steps=8):
    by_name = {t.__name__: t for t in tools}
    messages = [{"role": "system", "content": system},
                {"role": "user", "content": task}]
    for step in range(max_steps):
        msg = chat(messages, tools=tools).choices[0].message
        messages.append(msg.model_dump(exclude_none=True))
        if not msg.tool_calls:
            return msg.content          # the model is done
        for call in msg.tool_calls:
            result = call_tool(by_name, call.function.name,
                               call.function.arguments)
            messages.append({"role": "tool",
                             "tool_call_id": call.id,
                             "content": result})
    return None                         # the loop is done

Two exits

The model stops calling tools, or the budget runs out. Production loops add time and cost budgets.

The history is the memory

Every step resends everything. That's why Day 2 is about context.

call_tool never raises

Unknown tool, bad JSON, wrong arguments, ToolError: each comes back as {"error": …} for the model to handle.

Making the loop safe to run

Budgets and errors as observations

Step budget

max_steps stops a model that keeps calling a tool that never satisfies it. Return a clear "stopped after N steps", not silence.

Cost and time budgets

Stop when the run's cost or wall time crosses a limit. Input tokens grow every step, so cost grows faster than linearly.

Errors are data

A failed verification goes back as a result, so the model asks for the right mobile instead of crashing the loop.

        turn = adapter.step(state, tools, model)
        if not turn.calls:
            return Run(turn.text, ...)

get_permit raises because the mobile number is wrong. What should the loop do?

Raise, so the developer sees the bug
Retry the same call until it succeeds
Return the error to the model as the tool result, so it can ask the person for the right number
C. A tool error is an observation about the world, not a bug in the loop. Write error messages as instructions ("ask for the registered mobile"), and keep bugs (exceptions in your own code) out of the model's view.
