The cost model of an agent

Every step resends everything

step 1system + tools + user
step 2system + tools + user + call + result
step 3system + tools + user + call + result + call + result
step 4… + call + result + call + result + answer

Input dominates

Agents read far more than they write. Manus (a general-purpose agent product) reported about 100 input tokens per output token (2025).

Quadratic growth

Step n pays for everything before it, so a 20-step task costs far more than 20 times one step.

Three levers

Send less (select, compress), send it cheaper (cache), send it elsewhere (isolate in a sub-agent).

Bigger is not better

Effective context is smaller than the context window

  • Context rot (Chroma, Jul 2025): across 18 models, accuracy fell as input length grew, even on simple retrieval and repetition tasks.
  • Distractors that look like the answer hurt more than unrelated text.
  • A million-token window lets you send a million tokens; it doesn't make the model use them well.
The working rule. Find the smallest set of high-signal tokens that makes the next step likely to succeed. Anthropic's phrasing (Effective context engineering for AI agents, Sep 2025): context is a finite resource with diminishing returns.
Don't quote a specific "effective length" number: it varies by model, task and position. The point is the curve, not the number. Students measure their own on Day 3 with evals.
How long contexts fail

Four context failures

Poisoning

A hallucination or a wrong tool result enters the context and is repeated as fact. Rafeeq "remembers" a fee it computed wrongly three turns ago.

Distraction

So much history that the model repeats past actions instead of reasoning about the new step.

Confusion

Irrelevant content (40 tools, five long passages) pulls the answer off course.

Clash

Parts contradict each other: an old policy version, or an early guess the model later corrected.

Drew Breunig, How long contexts fail and How to fix your context (Jun 2025).

Background · what a provider can reuse

Reading a prompt is work, and a repeated start can be reused

  • Before writing a single token, the model processes every input token and keeps an internal state for each one (the KV cache).
  • The state for token n depends only on tokens 1…n. Two requests that start with the same tokens share that state.
  • So a provider can keep the state for a prompt's beginning (the prefix) for a few minutes and skip recomputing it: faster first token, cheaper input.
call 1[system + tools + policies] + question A → computed, stored
call 2[system + tools + policies] read from cache + question B → only B computed
call 3[new timestamp + system + …] → nothing matches from token 1: all recomputed
No transformer internals needed: the one fact that matters is that processing runs left to right, so only an identical beginning can be reused. That single fact explains every rule on the next slide.

Context engineering meets PDPL

A summary is a new copy of personal data

Sara (ID ending 4821, mobile 0501234821) asked about REN-10482; status under review…
Identity verified for REN-10482. Status under review, decision due 2 Nov 2026. Sara asked about a 35 m² structural change: +35 SAR (POL-02).

  • Data minimisation (PDPL: keep personal data only as long as needed) applies to what you keep in context, not only to your database.

Background · the first remedy from Day 1

Retrieval: put the right passages in the context

Splitdocuments into chunks (a section, a paragraph)
→

→
Insertthe top few into the prompt, with their IDs

RAG

Retrieval-augmented generation: the knowledge comes from your documents at question time, not from training. It works around the knowledge cutoff and most hallucination about your data.

The hard part is the search

If the right chunk isn't retrieved, the model answers without it, or from a wrong one. Retrieval quality caps answer quality.

Two architectures

RAG as a pipeline vs. retrieval as a tool

Pipeline (classic RAG)

Question
→
Retrieve k
→
Answer

Always retrieves, once, with the user's words. Predictable and cheap; fails on multi-hop questions and when the user's words aren't the document's words.

Tool (agentic retrieval)

Question
→
Search?rewrite, repeat
→
Answer

The model decides whether to search, with what query, and whether to search again. Handles multi-step questions; costs more steps and needs good tool descriptions.

Rafeeq uses both: search_policies is a tool, and Day 4's permit-review graph uses a fixed retrieval step where the path is known.
Background · two ways to score a chunk

Search by shared words, or by similar meaning

Keyword search: BM25

  • A chunk scores higher for containing the query's words, more so for rare words; long chunks are normalised.
  • Exact IDs and numbers win (FZ-2, POL-07).
  • Needs shared words: "price" won't find "fee", Arabic won't find English.
bm25s

Meaning search: embeddings

  • An embedding model turns text into a vector (a few hundred numbers) so that similar meanings land close together.
  • Score = closeness of the question's vector to each chunk's (cosine similarity).
  • A multilingual model puts Arabic and English in one space. potion-multilingual-128M runs on a CPU in milliseconds.
model2vec · Hugging Face Hub
An embedding model is a different, much smaller kind of model than an LLM: it outputs a vector, not text. Give the intuition with an Arabic and an English sentence about fees landing near each other and a sentence about food trucks landing far away.
Making search work on Madar's policies

Normalise Arabic, fuse rankings, measure

Hybrid search (RRF)

Run both, then fuse the two rankings with reciprocal rank fusion: score = Σ 1 / (60 + rank). It uses ranks, not raw scores, so nothing needs calibrating. A strong default.

A retrieval eval

Questions with the correct ("gold") policy ID. recall@k = the share of questions whose gold chunk is in the top k results.

DIACRITICS = re.compile("[ً-ْـ]")
def normalize(text):
    text = DIACRITICS.sub("", text.lower())
    return text.translate(str.maketrans(
        {"أ": "ا", "إ": "ا", "آ": "ا", "ة": "ه", "ى": "ي"}))
Evaluate before you choose. 16 bilingual questions are enough to see a difference. Arabic keyword search needs the normalisation on the left (diacritics, letter variants). With 24 chunks every method hits in the top 3, so compare recall@1.
How coding agents search

Agentic search: list, grep, read

user"Which food-truck zone is closed during exam weeks?"
callgrep_policies("exam")
result[{"policy_id": "POL-09", "line_no": 6, "line": "| FZ-2 University Gate | … | closed during exam weeks |"}]
final"FZ-2 University Gate (Al-Jamiah) closes during exam weeks (POL-09)."

Wins when

Documents are structured, identifiers are exact, the corpus is navigable, and freshness matters (no index to rebuild). Claude Code and Codex search code this way.

Loses when

Thousands of documents, fuzzy or cross-lingual phrasing, tight latency. More steps means more tokens.

And when it all fits?

Ten policies are ≈4,400 tokens. Putting them all in a cached system prompt can beat any retriever.

Grounding

Cite the source, then check the citation

  • Every retrieved passage carries its policy ID; the system prompt asks the model to cite it.
  • A citation is checkable: does the cited policy contain the claim? Day 3's eval tests "answer contains 1,000 and cites POL-07".
  • Some APIs return structured citations (Anthropic search results and citations, OpenAI file search annotations). With function tools you design them yourself.

The integration problem

M hosts × N tools, or M + N

  • Without a protocol, every agent host writes its own connector for every system.
  • MCP (Anthropic, Nov 2024) standardises how a host discovers and calls tools, reads data and fetches prompt templates.
  • Now governed by the Agentic AI Foundation (Linux Foundation), with AGENTS.md and A2A.
  • Supported by Claude, ChatGPT and the OpenAI Responses API, Gemini, VS Code, Cursor, OpenClaw, Hermes and most harnesses.
Background · the plumbing MCP is built on

JSON-RPC messages over a pipe or over HTTP

→ {"jsonrpc": "2.0", "id": 7,
   "method": "tools/call",
   "params": {"name": "compute_fee",
              "arguments": {"permit_type": "EVT",
                            "event_days": 3}}}
← {"jsonrpc": "2.0", "id": 7,
   "result": {"content": [{"type": "text",
              "text": "3000 SAR"}]}}

JSON-RPC: a tiny convention for remote calls. A method and its params go out; the reply carries the same id with a result or an error.

stdio

The host starts the server as a subprocess and exchanges JSON lines over its stdin and stdout. Local, no network.

Streamable HTTP

The server is a web endpoint (POST /mcp). Remote, shared, needs authentication.

Host · client · server

The host is the app with the model (your loop, Claude Code). It opens one client connection per server.

What a server offers

Three primitives, three different deciders

PrimitiveWhat it isWho decides to use itMadar server
Toolsfunctions with a JSON Schemathe modelget_permit, compute_fee, …
Resourcesdata addressed by URI (or URI template)the host (or the user)madar://policies, policy://{policy_id}
Promptsparameterised templatesthe user (e.g. a slash command)triage_email

Clients can offer features back to servers too: sampling (the server asks the host's model to generate), elicitation (the server asks the user a question) and roots (the folders the server may work in). Transports: stdio for local subprocesses, Streamable HTTP for remote servers.

Spec revision 2026-07-28

MCP went stateless

POST /mcp
Content-Type: application/json
MCP-Protocol-Version: 2026-07-28
Mcp-Method: tools/call
Mcp-Name: compute_fee

{"jsonrpc": "2.0", "id": 3, "method": "tools/call",
 "params": {"name": "compute_fee",
  "arguments": {"permit_type": "EVT", "event_days": 3},
  "_meta": {
   "io.modelcontextprotocol/protocolVersion": "2026-07-28",
   "io.modelcontextprotocol/clientCapabilities": {}}}}
  • No initialize handshake, no session ID. Each request carries its version and capabilities in _meta.
  • server/discover tells a client what the server offers, when it wants to know.
  • Method and tool name in headers, so gateways can route and authorise without parsing bodies.
  • Servers that need user input mid-call return an "input required" result; the client retries with the answer (multi round-trip requests). Long-running tasks moved to an extension.
  • Any request can hit any replica behind a load balancer.

Before you connect a server

Code you run, and text your model reads

Tool poisoning

A prompt injection in a tool description enters your model's context the moment you list tools.

Rug pulls

A server changes its tools after you approved them (listChanged).

Over-broad credentials

A local server runs with your user's permissions and tokens.

  • Who publishes it? Readable source, pinned version?
  • Read every tool description before enabling it
  • Least privilege: read-only tools first; scoped tokens
  • Approval for tools that write or send (the ✱ in Lab 2.4)
  • Log calls; alert when the tool list changes

Day 2 recap

The right tokens, at the right time

  • Context is a budget: every step resends everything; effective context is smaller than the window.
  • Write, select, compress, isolate, and keep a stable prefix for caching.
  • Retrieval: evaluate first; hybrid is a strong default; agentic search for structured, exact lookups.
  • Memory is a contract you implement: safe paths, caps, and never personal data.

  • MCP: tools, resources, prompts over a stateless protocol; review servers like dependencies.
